# match-signals

C++17-библиотека для обработки футбольных событий и вызова двух внешних моделей:

```text
Sportradar XML → SportsUpdate → история матча → ProbabilityModel
                                                    ↓ ProbabilityWin
Polymarket /book → котировки ────────────────→ DecisionModel
Портфель + ограничения ─────────────────────→        ↓
                                               TradeDecision
                                                    ↓
                                          проверка и резерв
                                                    ↓
                                 внешний исполнитель → OrderReport
```

Обучение, ML-инференс и торговая стратегия подключаются через C++-функции.
Внутри движка данные передаются по `const&`; JSON и XML используются только
на границе с поставщиками. Пример содержит фиксированные ответы моделей
для проверки связки, а не реализацию ML или прибыльной стратегии.

## Сборка

Нужны CMake ≥ 3.16, компилятор C++17, libcurl с TLS и libxml2.
На macOS эти библиотеки доступны в SDK Xcode. На Debian/Ubuntu нужны пакеты
`libcurl4-openssl-dev` и `libxml2-dev`. nlohmann/json 3.12.0 находится в
`third_party/` вместе с MIT-лицензией; сборка не скачивает зависимости.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j 4
ctest --test-dir build --output-on-failure
./build/pipeline_example
```

Пример работает локально, не требует ключей и не отправляет ордеров:

```text
BUY YES count=5 limit=0.6 revision=1
Reserved: cash=100 available=97
Filled: cash=97 position=5
```

| `engine.hpp`, `engine.cpp` | Владение состоянием и последовательность вызовов моделей |
| `sports_feed.hpp`, `sports_feed.cpp` | TLS-соединение, вход, подписка и heartbeat Sportradar |
| `sports_xml.cpp`, `sports_xml_parse.cpp` | Сборка сообщений/страниц и разбор XML |
| `market_data.hpp`, `market_data.cpp`, `order_book.cpp` | Опрос Polymarket с заданным интервалом и разбор стакана |

Цель CMake `match_signals` содержит ядро без внешних зависимостей.
`match_signals_feeds` добавляет сетевые адаптеры и парсеры.

## Контракт моделей

`ProbabilityModel` получает весь `MatchContext`: текущий счёт, тайм, игровое
время, карточки, состояние источника и историю `SportsEvent`. История хранится
один раз внутри `TradingEngine`. Обычная дельта не копирует её целиком.
Новые UUID добавляются, существующие исправляются, `1044/refuuid` удаляет
событие и не даёт повторной дельте его восстановить. Полный снимок заменяет
историю; после потери соединения перед дельтами нужен новый полный снимок.
Порядок — `stime`, при равных значениях сохраняется порядок получения.
Дополнительные атрибуты событий сохраняются для модели; нестабильный числовой
`id` отбрасывается, идентичность определяется по UUID.

Модель возвращает `ProbabilityWin{match_id, revision, home_win, draw, away_win}`.
Три конечных числа должны лежать в `[0, 1]` и давать сумму 1 с погрешностью
не более `1e-6`. Здесь вероятности относятся к исходу основного времени
с добавленными минутами. Дополнительные таймы и пенальти в этот контракт не входят.
`yes_probability(Target)` выбирает вероятность соответствующего исхода;
вероятность No равна `1 - yes_probability`.

`DecisionModel` получает вероятности, `MarketState`, `PortfolioState` и
`RiskLimits`. Результат — `std::optional<TradeDecision>`:

```cpp
TradeDecision{
    market.market_id,
    Action::Buy,
    Outcome::Yes,
    decimal("5"),
    decimal("0.60")
};
```

`std::nullopt` означает отсутствие действия. Ошибка модели или неверный ответ
вызывает исключение. Движок присваивает решению версии матча и котировок,
проверяет свежесть после инференса, размер, шаг цены, доступные средства и
лимиты. В перерыве и вне первого/второго тайма торговые решения не выдаются.
Соответствие `market_id`, токенов Yes/No, матча и правила расчёта контракта
задаёт вызывающее приложение: библиотека не угадывает его по названию рынка.

## Портфель и исполнение

Начальное состояние задаётся `set_portfolio(cash, positions)`. Позиции
индексируются конкретным `asset_id`, а не общим названием Yes/No.
Все денежные значения и количества — целые `Units` с масштабом `1'000'000`:
`decimal("0.60") == 600'000`. Количество ордера кратно 0.01 доли;
минимальный размер и шаг цены берутся из стакана.

`TradeDecision` — предложение. Перед отправкой внешний исполнитель вызывает
`reserve_order(client_order_id, decision, fee_budget)`. Этот метод повторно
проверяет версии, свежесть, доступные средства и лимиты. Затем резервирует
деньги для покупки или токены для продажи. Несколько предложений могут
претендовать на один баланс: резервировать их нужно последовательно.
Комиссию оценивает исполнитель; библиотека не рассчитывает тарифы площадки.

После подтверждения исполнения вызывается `update_order(OrderReport)`:

- `filled_count` — суммарно исполненное количество по этому ордеру;
- `cash_total` — суммарные фактические расходы на покупку с комиссией либо
  суммарная выручка от продажи после комиссии;
- `terminal` — окончательный отчёт с учётом всех исполнений и комиссий.

Балансы меняются только по подтверждённым отчётам. Повторные отчёты
идемпотентны. Частичное исполнение сохраняет резерв, окончательное освобождает
остаток. При отклонённом или отменённом неисполненном ордере передайте
нулевые итоги и `terminal=true`. Таймаут отправки не доказывает отмену:
резерв нужно сохранять до выяснения состояния у площадки.
Завершённые ордера остаются в памяти для защиты от повторных ID/отчётов.
Согласование отчётов после перезапуска и хранение состояния на диске относятся
к внешнему исполнителю.

## Подключение источников

`SportsFeedClient` подключается к XML push-feed Sportradar/Betradar по TLS,
проверяет сертификат, отправляет переданный `login_xml` и подписывается на
заранее забронированные матчи. Сам клиент не бронирует платные матчи.
`connect()` ожидает ответ на вход, `poll(wait)` возвращает готовый
`SportsUpdate` или `nullopt`. Heartbeat обслуживается во время опроса.
Потеря соединения, таймаут, отказ подписки или ошибка протокола закрывают
клиент и вызывают исключение. При такой ошибке вызовите
`engine.feed_disconnected()`, затем повторно `connect()`; это восстановит
подписку и получение полного снимка. Паузы между попытками выбирает приложение.

Клиент принимает полный снимок, дельты, `deltaupdate`, `matchdata` и
`full_paginated/partial`. До последней страницы модель не вызывается.
Буфер и совокупность собираемых снимков ограничены 8 МиБ, число страниц — 256;
превышение приводит к ошибке, а не выдаче неполной истории. XML с DTD/внешними
сущностями запрещён. В конфигурации поставщика нужны UUID, `refuuid` и время
матча в полном снимке. Изменение счёта/времени в историческом `deltaupdate`
не откатывает текущее состояние матча.

`MarketDataClient` принимает `MarketSubscription` с двумя реальными asset ID
(сначала Yes, затем No) и интервал. Первый `poll()` получает оба стакана
через HTTPS `/book`; ранние повторные вызовы возвращают `nullopt`. Опрос
запланирован с постоянным интервалом; пропущенные из-за медленного I/O
моменты пропускаются без серии догоняющих запросов. Стаканы получаются
последовательно и имеют отдельное время получения. Медленный ответ не
становится искусственно свежим: возраст отсчитывается от начала запроса.
Ошибка не заменяет прежние котировки пустыми; их возраст продолжает расти.
В тестах вместо сети можно передать `FetchBook`.

Клиенты выполняют синхронный I/O. Их вызовы и локальные модели могут
блокировать вызывающий поток. Движок рассчитан на одного владельца:
приложение само организует I/O-потоки и последовательно передаёт обновления
движку. Не удерживайте ссылки на его состояние после возврата из модели и
не меняйте движок из callback модели. Автоматическая отправка и подпись
ордеров, сеть для удалённых моделей, база данных и обучение не включены.

Протоколы описаны в [Sportradar Live Data](https://docs.sportradar.com/live-data/introduction/best-practice-guide),
[настройках XML](https://docs.sportradar.com/live-data/introduction/xml-configuration)
и [Polymarket](https://docs.polymarket.com/market-data/prices-order-books).
Доступ к закрытому спортивному feed и реальные модели для тестов не использовались.
Возраст данных проверяется по локальному монотонному времени получения;
задержка скаута и прибыльность стратегии этими проверками не подтверждаются.
